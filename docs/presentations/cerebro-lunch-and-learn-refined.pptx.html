What Cerebro does, in plain language

Cerebro collects operational and security signals from external systems, normalizes them into durable records, projects useful relationships into a graph, and exposes findings, reports, APIs, CLI commands, SDKs, and MCP tools on top.

Collect

Cloud, SaaS, identity, endpoint, vulnerability, compliance, and workflow signals.

Make durable

Persist current state, append replayable events, and track runtime progress.

Explain risk

Produce graph context, durable findings, evidence, reports, and actions.

Vocabulary

The nouns you need before reading code

Source

Integration code that checks config, discovers objects, and reads pages of typed events.

Runtime

A persisted, tenant-scoped source configuration plus progress state.

Event

A replayable observation emitted by a source and accepted by runtime sync.

Claim

Normalized state produced by runtime or SDK paths.

Finding

A durable, remediable risk state with lineage, fingerprinting, and evidence.

Graph projection

Neo4j rows rebuilt from durable state so relationships can be queried safely.

Keep these separate: raw event, current state, graph projection, finding outcome. 4

Part 1: Source CDK

Sources are the only path to the outside world

The source contract

  • Spec(): stable identity and metadata.
  • Check(): validate config and credentials.
  • Discover(): list discoverable objects.
  • Read(): return one page of events plus cursor data.

The boundary

  • No direct store writes.
  • No graph projection.
  • No finding IDs or runtime IDs.
  • No custom persistence or replay logic.
A source describes what it saw. Cerebro decides how to persist, replay, project, and evaluate it.

Part 3: Durability

Each store has one job

Store
What it is for
What it is not for
JetStream
Append log for source runtime sync, replay, and workflow events.
Not a query model for current findings or reports.
Postgres
Current state: runtimes, claims, findings, evidence, reports, evaluation runs.
Not the place for arbitrary graph traversal.
Neo4j/Aura
Graph projection and bounded relationship queries.
Not the source of truth and not a fourth durable store.
If Neo4j disappears, Cerebro should be able to rebuild graph state from durable records.

Failure model

Why the sync order matters

If this fails
What should be true
Why it matters
Source read
No append, no projection, no cursor advance.
The page can be retried safely.
Event validation
Bad records are rejected or quarantined.
Invalid shape does not poison durable state.
Append
Projection and cursor advancement do not proceed.
No unreplayable graph or current-state write.
Projection
Cursor does not advance until configured projection succeeds.
Operators can repair without losing the page.

Part 4: Findings

A finding is an actionable risk state

Good finding shape

  • Current condition, not just an event that happened once.
  • Stable fingerprint anchored to a durable resource or graph path.
  • Clear affected asset, identity, control, or owner.
  • Evidence and enough context to remediate.

How evaluation works

  • Rules are registered in a discoverable catalog.
  • One rule is evaluated per request.
  • Evaluation runs are persisted for auditability.
  • Clients read persisted findings after evaluation.
Do not turn every upstream alert into a finding. Turn durable, remediable risk into a finding.
Docs: docs/domains/findings-platform-architecture.md 10
Part 5: Graph

The graph answers relationship questions

Neo4j projection helps Cerebro answer questions that are hard to express from one raw event or one current-state row.

Reachability

What can this identity, endpoint, package, account, or resource reach?

Impact

If this vulnerability or exposure exists, what assets or owners are affected?

Risk composition

Which separate signals combine into a higher-priority risk path?

  • Use platform routes and bounded graph operations where possible.
  • LLM-authored Cypher is read-only, tenant-scoped, procedure-free, and LIMIT-bounded.
  • Rebuilds should start as dry runs and rely on durable records.
Docs: docs/domains/graph-operations.md, internal/graphagent/validator.go 11
Common mistakes

What to avoid when changing Cerebro

Putting provider-specific orchestration into platform services.
Letting a source write to Postgres, JetStream, or Neo4j directly.
Advancing a cursor before accepted events are safely appended and projected.
Treating Neo4j as authoritative current state.
Creating findings that mirror raw vendor alerts one-to-one.
Fingerprinting findings on event IDs, timestamps, run IDs, or display names.
Adding graph queries without tenant scope, limits, or rebuild thinking.
Growing bootstrap with domain behavior instead of request mapping.
Docs: docs/engineering/non-goals.md and AGENTS.md finding guidance 12
Reviewer checklist

Before approving a Cerebro change, ask

What is the durable record for this write?
Can graph state be rebuilt without treating Neo4j as source of truth?
Does runtime progress advance only after safe append and projection?
Is tenant scope enforced before domain logic runs?
Does source code stay inside the Source CDK boundary?
Is finding identity stable across replay and provider quirks?
Is bootstrap only mapping transport, auth, and dependencies?
Does this cross a documented non-goal?
